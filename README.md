## 起動

Node.js 20以上とPython 3がある環境で実行します。

```sh
npm test
npm run build
npm start
```

## Google Cloud設定（利用者自身で行う操作）

Google Cloudのプロジェクト作成・同意画面・利用アカウントの認証は、利用者のGoogleアカウントで行ってください。課金契約や有料サービスを追加する必要はありません。APIの割り当て制限は適用されます。

1. [Google Cloud Console](https://console.cloud.google.com/) にログインし、新規プロジェクトを作成・選択します。
2. 「APIとサービス」→「ライブラリ」で **Google Calendar API** を検索し、有効化します。
3. **Google Auth Platform**（旧「OAuth同意画面」）で初期設定します。
   - Branding：アプリ名 `KonDate`、サポートメール、開発者連絡先。
   - Audience：個人利用ならExternal。テスト状態では **Test users** に実際に使うGoogleアカウントを追加します。家族と使うなら家族のアカウントも追加します。
   - Data Access：次の2スコープを追加します。
     - `https://www.googleapis.com/auth/calendar.calendarlist.readonly`
     - `https://www.googleapis.com/auth/calendar.events`
   - Internalは対象のGoogle Workspace組織内に限られます。
4. Clients → Create client → Application type **Web application**。
5. **Authorized JavaScript origins（承認済みJavaScript生成元）** に以下を追加します。
   - 本番：`https://suzu2384.github.io`
   - 開発時：`http://localhost:5173`
   - URLのパス `/kondate/` や末尾スラッシュは入力しません。
   - ポップアップ型Token Modelを使うので、この実装ではリダイレクトURIやクライアントシークレットを使用しません。
6. 発行された **Client ID**（末尾が `.apps.googleusercontent.com`）をコピーします。
7. KonDate → 設定 → Google OAuthクライアントIDへ貼り付け →「Googleに接続」。カレンダー一覧とイベント読み書きの両方を許可します。
8. 利用するカレンダーを選択します。選択後に履歴を取得します。料理以外の予定の誤取り込みを避けるため、献立専用のカレンダーが便利です。カレンダー作成はGoogleカレンダー側で行ってください。
9. 別の端末では同じClient IDを設定し、同じカレンダーを選択します。共有カレンダーを家族が編集する場合は、Googleカレンダー側でその人へ編集権限を付与してください。

公開運用に切り替える場合、Googleのスコープ分類・ユーザー数・対象によってOAuth検証やプライバシーポリシー等の要件が変わります。Google Auth Platformの表示に従って設定してください。本アプリは審査済みアプリであることを前提にしていません。テスト状態に追加していないアカウントでは接続できません。

### 認証の扱い

公式のGoogle Identity Services Token Modelを使用します。短命のアクセストークンはメモリと同一タブの sessionStorage に一時保存し、F5による再読み込み時に復元します。localStorage・Cookie・Service Workerキャッシュ・書き出しファイルには保存しません。リフレッシュトークンは使いません。トークン有効期間中は再利用し、同意を毎回強制する `prompt=consent` は設定しません。

Googleの公式仕様に合わせ、トークンの有効期限が切れた後はユーザー操作による再接続が必要です。F5の再読み込みでは有効な一時トークンを同じタブ内で復元し、カレンダー一覧と選択済みのカレンダーを再同期します。セッションの保存が制限されるブラウザや新しいタブでは再接続が必要な場合があります。GitHub Pagesだけで常時無操作の更新を実現する仕組みは実装していません。

「接続を解除」はこのアプリ内のトークンを破棄します。Google側の権限自体を撤回したい場合は [Googleアカウントの接続管理](https://myaccount.google.com/connections) を使います。

### 接続できないとき

- `origin_mismatch`：スキーム・ドメイン・ポートを確認。生成元に `/kondate/` を含めない。
- アクセス拒否：テストユーザー登録、対象アカウント、同意したスコープを確認。
- 403：APIの有効化、カレンダーの編集権限、利用制限を確認。
- 認証ウィンドウが出ない：ポップアップ許可を確認。iPhoneホーム画面版ではSafariでも試す。
- 認証切れ：再接続して下書きから保存を再試行。
- 競合表示：ほかの端末で変更されています。下書きを維持したまま同期し、最新の予定を確認してください。古い編集をそのまま強制上書きする機能はありません。必要なら入力を控え、下書きを破棄して最新の予定を開き直してください。

## 使い方

### カレンダー・実績

- 月表示で日付を選択。スマートフォンは詳細ダイアログ、PCは右ペインに表示。
- 「実績を登録」は当日が初期値。「この日に登録」は選択日が初期値。
- 主菜・副菜・汁物などを複数登録。料理名はマスターの候補から選択可能。
- 調理実績と献立案を区別。献立案は調理回数・最終調理日に加算しません。
- 保存時にGoogleへ送信。通信失敗時は入力内容と登録IDを保持。再試行は同じIDで行い、重複イベントを防止します。
- 同期は指定開始日から現在年の翌年末まで全ページを取得し、画面表示用のメモリを更新します。さらに先の年を表示して同期すると取得範囲が延びます。削除や他端末の変更も反映します。日付境界の取得は日本時間、時刻付き予定の表示日は選択カレンダーのタイムゾーン基準です。
- 複数料理は1イベントにまとめるため、1回の登録が部分成功することはありません。

### 既存のGoogleカレンダー予定

選択した**献立用カレンダー内の予定はすべて確定した献立・調理実績**として扱います。初回取り込み操作やローカル承認は不要です。既存のタイトルから料理名を読み取り、履歴の集計にも利用します。

既存の予定をアプリで編集した場合は、元のGoogleカレンダーの**同じイベントを更新**します。日付・時刻などは維持し、料理名と分類をアプリの形式で保存します。削除は明示的な確認操作後にGoogleカレンダーへ反映します。献立に関係しないカレンダーは「その他のカレンダー表示」へ指定してください。

履歴の取得結果はメモリ内のみで保持し、F5でGoogleから再取得します。端末に保存するのは設定・入力途中の下書き・料理マスターの補足情報などです。取得したGoogleカレンダーの予定自体を端末に永続保存しません。

### 料理マスター

実績から正規化した料理名で集約し、最終調理日・回数・日付一覧を自動計算します。NFKC、空白除去、大文字小文字の統一に対応。意味が同じ別表記は料理マスターの名前編集で統一します。表記統一・食材・調理法・ジャンルの補足は端末設定です。元のGoogleイベントを一括書き換えません。

初期候補は履歴とは別に40品を同梱。設定で無効化できます。「未調理」は取得対象の確定履歴に出ていないことを意味し、取得期間外の実績までは判定しません。通常生成で新しい主菜を使いたい場合は料理マスターへの新規登録が必要です。AI生成では、条件を有効にするとAIが未登録の主菜を1品提案できます。

### 献立生成と編集

日付なしの1〜15日分、初期値7日。AI生成・通常生成ともに同じ日数プルダウンを使用します。AI／ルールベースの選択も保存し、次回起動時に復元します。スマートフォンでも日数・生成方法・ルール調整・生成ボタンを横1行に表示します。日数・ルール・分類ごとの品数を指定できます。

- 最近7日の実績を除外、30日以上作っていない料理を優先（変更可）。
- 生成内の重複を除外。食材・調理法・ジャンルの総数と直前の日・同日の構成にペナルティを付け、履歴スコアとランダム要素で選定。
- 未調理の主菜を少なくとも1品加える設定。
- 候補不足の場合、献立の未生成箇所は空欄のままとし、問題の理由や対処操作はステータスバーの詳細ダイアログに集約します。献立画面内には重複するエラー一覧を表示しません。ダイアログは右上の×から閉じ、下部は必要な対処ボタンだけを表示します。無断の条件緩和・重複はしません。
- 料理名を押して差し替え・追加・削除。○/●で固定、↻で個別再抽選、↑↓で日を交換。
- 全体再生成でも固定を維持。固定料理自体がルールに反する場合は残して警告。
- 「作ったら記録」で内容確認→実績保存。生成だけではGoogleへ送信しません。
- 下書きは端末へ自動保存。端末間で献立案を移す場合は設定・下書きの書き出し/読み込みを利用。

### テーマ・PWA

赤・黄・緑・シアン・青・マゼンタ・無彩色の7系統×ライト/ダーク。OS追従も可能です。画面全体は固定し、内容部分だけスクロールします。iPhoneはSafariの共有→ホーム画面に追加。Androidはブラウザのインストール/ホーム画面へ追加。

Service Workerは同一オリジンのアプリ資材だけをキャッシュします。Google APIや認証ライブラリをキャッシュしません。初回はオンラインが必要です。オフライン時は画面表示中の履歴・未確定の献立編集・テーマ変更を使えますが、ページ再読み込み後の履歴は再接続まで表示できません。実績のGoogle保存はオンライン時に明示的に行います。自動バックグラウンド送信はありません。

## AI献立生成（Firebase AI Logic / v1.5.0）

AIプロバイダーを分離し、現在の共通利用モード `shared-firebase` と将来の個人利用モード `personal` を別実装にしています。利用者はAI用APIキーを取得・入力しません。個人利用モードは現段階では実装の拡張点だけで、選択UIやキー管理はありません。

### 課金0円の絶対条件

- **みんコメとは別のFirebase / Google Cloudプロジェクト**を新規作成する。
- **Firebase Sparkプランで、Cloud Billingアカウントをリンクしない**。無料枠を超えた場合に有料利用へ自動切替する設計にはしない。
- **Gemini Developer APIの無料枠対応モデル `gemini-3.5-flash-lite` のみ**を使用。課金必須のモデル・Vertex AI・画像生成は使用しない。
- **請求先アカウントをリンクしないこと自体**が課金防止の条件。App Check・GitHub Actionsの承認フラグは課金状態を独立検証・強制できず、代わりにはならない。
- 課金契約を求められた場合は有効化せず、従来のルールベース献立生成だけを使う。後から請求先をリンクした場合は **AIを停止**する。
- 無料枠到達・リクエスト失敗・不正JSONでも、有料モデルへの切り替え・無限再試行を行わない。

参考：[Firebase AI Logic料金](https://firebase.google.com/docs/ai-logic/pricing?api=dev) / [対応モデル](https://firebase.google.com/docs/ai-logic/models?api=dev) / [Firebase App Check](https://firebase.google.com/docs/ai-logic/app-check)

### 開発者側の初期設定（未実施ならAIは無効）

1. [Firebaseコンソール](https://console.firebase.google.com/)でKonDate専用プロジェクトを新規作成。**Sparkプランかつ請求先未リンク**を確認し、Google Analytics・Hosting・Firestore・Cloud Functions等は追加しない。
2. Webアプリを登録し、Firebaseの公開Web設定（`apiKey`、`authDomain`、`projectId`、`appId`等）を控える。これはクライアント識別用の公開設定。**みんコメのGemini APIキーは絶対に使用しない**。
3. Firebaseコンソールの AI Services → AI Logic から **Gemini Developer API** を有効にする。請求先リンク/Blaze化が必要と表示された場合は中止する。
4. Firebase App CheckにWebアプリ用 **reCAPTCHA Enterprise** を登録し、`suzu2384.github.io` を許可ドメインとする。Security → App Check → APIs → Firebase AI Logic が **Enforced** であることを確認。reCAPTCHAの有料利用が必要と表示された場合は中止する。**App Checkデバッグトークンは公開しない**。
5. Google側のAI利用枠と割り当てを管理する。KonDateには端末単位の回数制限を設けないが、Gemini Developer APIの無料枠やレート制限はそのまま適用される。**不正利用防止にはApp Checkの強制を維持する**。
6. GitHubリポジトリの Settings → Secrets and variables → Actions → Variables に以下の**公開情報のみ**設定する。

   | 変数名 | 値 |
   | --- | --- |
   | `KONDATE_AI_FIREBASE_CONFIG` | Firebase Webアプリの公開設定JSON |
   | `KONDATE_AI_APP_CHECK_SITE_KEY` | reCAPTCHA Enterpriseの公開サイトキー |
   | `KONDATE_AI_SPARK_VERIFIED` | **Sparkかつ請求先未リンクを確認したときだけ** `true` |

7. Actionsの公開ワークフローを実行してPagesに反映。未設定時は共通AIモード無効、ルールベース生成と既存機能は変わらない。初期選択は「ルールベース」で、選択変更後は端末設定とDrive設定同期に保存する。

### 挙動・プライバシーと将来の拡張

- AIボタンを利用者が選んだ場合のみ、料理候補の**料理名・分類・調理回数・最終調理日・食材/調理法の属性**と献立条件・固定した料理だけを送る。Googleカレンダーの元の予定、住所/店名、認証トークン、保存した設定全体は送らない。
- AI生成で「未調理の主菜を1品以上加える」を有効にした場合は、AIに既存候補以外の**新しい主菜を1品**提案させる。主菜以外やそれ以外の料理は従来どおり候補限定。新しく提案された料理は下書きに含まれるが、料理マスターへ自動登録しない。調理実績として記録すると履歴の料理候補になる。通常生成は従来どおり料理マスターから選ぶ。
- AIの新規主菜を含む生成結果は、料理名・分類・未登録かどうかをチェックし、既存の `AIService` が重複・直近の実績・固定・品数などを検証する。検証に失敗するとメニューの下書きは更新しない。
- AI・通常生成ともに最大15日（初期値7日）。AIの端末別回数制限はなく、献立画面のAI説明文も表示しない。生成エラーはステータスバーに概要を表示し、タップすると原因・対処方法と「ルール調整」「料理マスター」「ルールベースに切替」など状況に応じた操作を表示する。ステータス通知は従来の文字列と詳細・ガイド・対処操作を持つ形式の両方をサポートする。Google側の無料枠とレート制限は維持する。
- 写真解析は今回の共通AIプロバイダーには実装していない（誤ってAIが有効化されないよう入口は非表示）。
- 将来の `personal` モードは `src/ai-provider.js` 経由で別プロバイダーを注入する。個人用APIキー・OAuthを現在の共有Firebaseコードに混ぜない。利用者に必要な手順や利用規約を別途確認したうえで追加する。

## v1.3.21：Drive自動同期の誤った競合警告を修正

Driveのファイル更新番号が端末内の記録と異なるだけでは競合とは判断しません。Google Driveから読み込んだ設定内容と端末内の設定内容について、更新日時を除いたSHA-256指紋を比較します。

- 実際の内容が同じ場合は、以前の未同期フラグや古いDrive更新番号が残っていても自動的に同期済み状態へ戻します。**1端末だけで発生する偽の競合警告**を修復するための処理です。
- 前回同期した設定内容の指紋を端末内に保持し、ローカル側だけの変更ならアップロード、Drive側だけの変更ならダウンロードします。両方で独立に変更した場合だけ競合警告を出し、無断で上書きしません。
- Driveへのアップロード後は、ファイル一覧が古い更新番号を返す場合に備え、アップロードの応答が返す更新番号を優先して使います。
- ネットワーク通信中に入力した内容があれば、変更を引き続き未同期として扱います。認証期限切れ時の固定ステータスバー・手動保存と復元はそのまま利用できます。
- 同時変更が重なった場合の手動での保存・復元は引き続き必要です。以前の未同期の変更とDrive上の設定が実際に異なる場合は、安全のため警告を残します。

## v1.3.22：月カレンダーの2段階タップとスワイプ

- 月カレンダーの日付は、最初のタップでその日付を選択・強調します。同じ日付をもう一度タップすると、実績の詳細と「＋ この日に登録」を含む詳細画面が開きます。初期状態で強調されている「今日」をタップする場合も初回は選択のみです。閉じた後は再度2回タップで開きます。
- 月カレンダーのマス目の上で**左へスワイプすると翌月、右へスワイプすると前月**を表示します。55px未満の短い移動、縦スクロールに近い動き、ゆっくりした長押しの動きは無視します。ダイアログ表示中や他のタブでは判定しません。
- スワイプと同時に日付が選ばれないようタッチ終了時のクリックを抑止します。月移動時は前のタップ履歴を破棄します。月矢印ボタンと「今日」ボタンは従来どおり使えます。手動のピンチズームに制限は加えていません。

## v1.3.23：選択済み日付のタップは1回で詳細を開く

前版の「常に2回タップ」方式を修正しました。すでに選択・強調表示されている日付を押した場合は、その**1回の操作で**日付の詳細・登録ダイアログを開きます。選択されていない日付では、1回目のタップで選択するだけです。画面を開いた直後から強調されている「今日」も、タップ1回で詳細を開きます。ダイアログを閉じても選択状態は維持され、次の1タップで再び開けます。前月・翌月への左右スワイプは維持しています。

## v1.3.24：外食記録と場所入力

Googleカレンダーの予定に「場所」が入力されている場合は外食の実績として扱います。調理履歴から料理マスターの候補を自動作成する際、場所ありの予定を除外します。料理マスターの調理回数と最終調理日にも加算しません。**予定・外食の履歴自体はカレンダーから削除せず、従来どおり表示・編集できます。** 同じ料理の場所なしの自炊実績は引き続きカウントします。

「調理実績を登録」「調理実績を編集」の両画面に「場所（任意・外食の場合に入力）」欄を追加します。入力値はGoogleカレンダーのイベントにあるネイティブな `location` プロパティへ保存され、既存のGoogleカレンダーで登録した場所も読み込みます。場所を消して保存すると空欄の自炊実績へ変更できます。異なる分類が異なるカレンダーへ書き込まれる場合も、場所を各イベントに引き継ぎます。従来の開始・終了時刻は変更しません。

料理マスターに手動追加したレシピや、あらかじめ用意した候補料理は、外食記録にかかわらず明示的な候補として残ります。つまり、レストランで食べたことだけを理由に、自宅でも作れる同名料理を永久に禁止する仕様ではありません。

## v1.3.25：月カレンダー簡素化と場所サジェスト

調理実績の場所欄では、オンライン時にOpenStreetMap由来の施設名・地名候補を表示します。**公開デモのPhoton API**を使用し、ブラウザから直接検索します。APIキーやサーバー、支払い設定は不要です。2文字以上を入力し、入力停止後約0.75〜1.2秒待ってから最大5件を取得します。APIへのアクセスは最短でも約1.2秒間隔とし、途中で入力が変わると古い検索を中止します。候補は名前と所在地を表示し、選択した店名をGoogleカレンダーの場所へ保存します。候補なし・通信失敗・オフライン時も自由に入力できます。Photon公開デモには可用性・日本国内の網羅性の保証がなく、負荷制限で検索が失敗することがあります。画面内にOpenStreetMapとPhotonのクレジットを表示します。

カレンダーは**月表示のみ**とし、上の「月表示／履歴一覧」切替、料理マスターへの入口を撤去しました。余白を月のグリッドへ渡し、PCでは右側の詳細パネルもコンパクトにして月カレンダーを広げます。料理マスターの管理機能は献立生成タブから利用できます。日付のタップ・左右スワイプは変わりません。日付セルの料理名は先頭の「・」を表示せず、長い名前も省略記号「…」を出さずに枠で切ります。

Googleカレンダーに「献立案」を書き込む分類・状態選択を削除し、新規登録はすべて調理実績になります。既存の「献立案」属性で保存された旧データは**Googleカレンダーから削除せず**、KonDate上の月表示や自炊履歴の生成候補からは無視します。「献立生成」タブは引き続き献立を組み立てるために残しています。

## v1.3.26：日本語の場所候補検索を修正

Photon公開APIは日本語を意味する `lang=ja` をサポートしていないため、現地表記を返す `lang=default` に変更しました。従来のv1.3.25で行った月表示中心の画面・献立案廃止・候補選択を含むすべての変更を継承した修正版です。既存のGoogle Calendarイベントには変更を加えません。
