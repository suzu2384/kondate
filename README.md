# KonDate

Googleカレンダーの調理実績を正本とする、献立作成・料理管理・買い物管理のPWAです。スマートフォンを優先し、PCでも利用できます。

このREADMEは**現行実装の仕様**をまとめたものです。変更履歴やバージョン別の説明、リポジトリ作成・初期構築の手順は記載しません。実際の挙動が変更されたときは、該当する仕様を更新してください。

## アプリ構成と運用上の制約

- GitHub Pages上で動作する静的Webアプリ。HTML、CSS、JavaScript（ES Modules）を使用し、独自バックエンドを設けない。
- カレンダーの実績と予定はGoogle Calendar API、端末間の設定バックアップはGoogle Drive API、家族共有はGoogle Drive APIとGoogle Sheets APIを利用する。
- Googleの認証はブラウザからOAuthトークンモデルで行う。カレンダー・ドライブの権限は用途に応じて取得する。
- AI献立生成は有効化されている場合だけFirebase AI Logicを利用する。AIが使えなくてもルールベース生成を提供する。
- 端末の設定、料理の手動登録、下書きなどはローカルに保持する。Googleカレンダーから取得したイベント履歴は永続キャッシュとして保存しない。
- アプリの主画面は「カレンダー」「献立」「料理」「買い物」「設定」の5タブ。

## カレンダー・実績

### 保存と分類

- 料理は分類IDで管理する。初期分類は「主菜」。分類の追加・名称変更が可能で、主菜は削除不可。
- 各分類に、書き込み権限のあるGoogleカレンダーを割り当てる。同一カレンダーを複数分類に割り当てられる。未設定の分類は新しい調理実績を書き込めない。
- 保存先カレンダーごとにGoogle Calendarイベントを作成する。複数分類が同じ保存先を指す場合はまとめられる。複数保存先への保存が一部だけ成功する可能性はあり、その場合は同期後に確認する。
- 新規実績のタイトルは料理名を「、」で連結した文字列。分類、材料系の属性ではなく**料理名・分類ID・主食材・調理法・ジャンル**を構造化データとしてイベント説明欄に持たせる。
- 自アプリのイベントは `extendedProperties.private.kondate = "1"`、調理実績は `state = "actual"` を使用。説明欄の `--- kondate:v1 ---` 以降にJSONを保存する。終日イベントの終了日は翌日（排他的）。
- 旧形式のイベントはタイトル・説明から可能な範囲で読み取る。過去の献立下書きイベントは調理実績に含めない。既存予定の日時は編集時にもできる限り維持する。

### 取得・表示・入力

- カレンダーは月表示。日付が未選択なら最初のタップは選択、選択済みなら1タップで詳細を開く。左右スワイプで月を切り替える。
- 日付の詳細は日付と「料理を登録」を同じ行に置き、調理実績・その他の予定をそれぞれ1件1行で表示する。同種の予定間には区切り線を置かず、種類の境界だけを分ける。実績には「編集」ボタン、その他の予定には閲覧用のタイトルとメモを表示する。「調理実績」「表示のみ」の冗長な表記は用いない。調理実績が0件の場合はその他の予定の有無に関係なく空状態を表示し、旧記録タブで使用した`icons/tabs/utensils.svg`を用いる。
- 調理記録は登録・編集・削除でき、分類と料理名を複数指定できる。料理候補は「現在の献立 → 料理マスター」の順。選択した分類以外の料理をサジェストしない。
- 料理名の候補は独自ポップアップで表示し、タッチとキーボードで選択できる。料理属性の補完は同じ分類で一致した料理に限定する。
- 「場所」が入力された予定は外食としてカウントし、自炊の調理回数・最終調理日・履歴由来の料理候補から除外する。外食自体はカレンダーに残り表示される。
- 場所候補はOpenStreetMap由来のPhoton公開APIをブラウザから問い合わせる。入力文字による絞り込みと自由入力に対応し、通信不能でも手入力は利用可能。
- その他のカレンダーは閲覧用として表示対象を選択できる。料理履歴には混ぜず、元の予定タイトルを勝手に書き換えない。
- アイコン付き予定プリセットはタイトル、メモ、アイコン、色、カレンダー、並び順を設定する。日付から予定を追加・削除する高速入力と、未保存操作のバッチ保存に対応する。 カレンダーの日付内では設定済みの優先順位を各グループ内で維持し、メモありの予定を先に1件1行、メモなしのアイコンを後に横並びで表示する。メモなしは日付セルの幅に応じて自動改行し、アイコンのない一般予定は1件1行で表示する。この表示順変更はプリセットの保存順・Googleカレンダーの予定内容を変更しない。
- カレンダーのメモありプリセットはメモなしと同じアイコンサイズ（PC 15px／スマホ 13px）で、メモ文字は料理名の文字サイズ（PC 13px／スマホ 9px）に合わせる。
- アイコン表示は、閲覧対象の別カレンダーでもタイトルのキーワード一致により適用される場合がある。この表示専用の照合と予定の保存先は別処理で、Googleへの書き込み先はプリセットで指定したカレンダーIDのみとする。
- 予定プリセットの初回登録ではGoogleカレンダーへの接続、登録先の書き込み権限、対象カレンダーの初回予定同期を確認し、確認できないときは配置せず理由を通知する。プリセット変更・削除前に保存待ちとなった追加操作は旧登録先へ送らず取り消しを通知する（削除操作は元のカレンダーに残す）。
- 自動更新の間隔と履歴の取得開始日を設定可能。アプリが非表示・オフラインの間にバックグラウンド同期を保証しない。

## 料理マスター

- 自炊実績から料理を集計し、名称の別名対応、手動追加、食材・調理法・ジャンル・レシピ・1人前の材料情報を管理する。
- 調理回数と最終調理日はGoogleカレンダーの実績から算出する。手動登録のみの料理は調理済みの実績にはならない。
- 料理の検索、分類での絞り込み、表示対象（献立・買い物・すべて）切替に対応する。
- 主食材などの補足情報や手動追加は端末・設定バックアップの対象。料理名の表記統一時には対象となるカレンダーの履歴更新も行う。
- 料理タブから買い物対象の料理を追加・解除する。材料未登録の場合は登録を案内する。

## 献立生成

- 献立タブのルールベース／AI生成方法は上部の2択アイコントグルで切り替える。ルールベースには `icons/actions/cpu.svg`（添付のまま）、AIには既存の `icons/tabs/bot.svg` を使用し、現在の選択を設定・ドライブバックアップに保持する。AI未設定・生成中は該当する切り替えを無効にする。日数・ルール設定・生成・共有は従来どおり上部の1行を維持する。
- 初期7日・最大15日。分類ごとの1日の品数を指定し、ルールベースとAI方式を選ぶ。
- ルールは未調理期間の優先、直近実績の除外、同一献立内の重複防止、食材・調理法・ジャンルの偏り軽減、未調理の主菜の追加に対応。
- ルールベースでは料理マスターと利用可能な初期候補、過去の調理日、属性、固定済み料理を用いて候補を選ぶ。条件を満たせないときは無断で条件を緩和せず、通知から修正を案内する。
- 日ごとの料理の編集、再抽選、固定、日付間の入れ替えに対応。生成結果は下書きであり、生成しただけではGoogleカレンダーへ保存しない。
- AIは `src/ai-provider.js` でプロバイダーを分離し、設定がある場合だけ `shared-firebase` を有効化。公開設定は `src/ai-config.js` のビルド生成物から取得し、利用者にAPIキー入力を求めない。
- AIは `gemini-3.5-flash-lite` を指定し、取得した料理候補・分類・調理履歴・料理属性・ルール・固定状態などの必要情報を送る。認証トークンやGoogleカレンダーの生データ、場所情報は送らない。
- AI回答は日数、分類、品数、重複、直近実績などを検証し、必要に応じて制限付きで補完する。AIが提案した新しい主菜は実績登録まで料理マスターへ自動追加しない。
- AI未設定、サービスエラー、利用枠超過時にもルールベース生成は利用可能。有料モデルへの自動切替は行わない。写真解析は現状の画面に提供しない。
- AI構成の運用前提は、独立したFirebase Sparkプロジェクトで請求先をリンクせず、App Checkによる保護を有効化すること。GitHub Actions変数は公開可能なFirebase設定とサイトキー、確認用フラグを使い、秘密鍵をフロントエンドへ埋め込まない。

## 買い物リスト

- 料理タブで明示的に選んだ料理について、登録された1人前の材料を人数倍して集計。人数は1〜30人。
- 材料名の表記揺れと換算可能な単位を正規化して合算し、換算不可の値を勝手に丸めたり結合したりしない。
- 手動の買い物項目も扱う。表示は「未購入」「購入済」「除外」の3状態。
- 購入状態は材料と数量の識別情報を用いて保持するため、材料や分量が変わった際の誤った購入済み扱いを避ける。
- 家族共有はGoogleスプレッドシートを利用し、設定した間隔で表示中の変更を確認する。

- 買い物タブ上部のアイコントグルで「買い物リスト」と「価格管理」を切り替える。アイコンはそれぞれ `icons/actions/shopping-basket.svg` と `icons/actions/receipt-japanese-yen.svg` を利用し、メインタブは増やさない。価格管理では食材検索・絞り込み後の件数・価格追加を上部の同じ操作行に配置する。下部の操作ボタン領域は買い物リストと同じ高さで維持し、価格管理で不要な状態別ボタンは表示せず空欄にする。
- 価格管理には料理マスターの全食材、買い物へ手動追加した品目、既存の登録価格を一覧表示する。食材名で検索し、数量・単位・税込価格を手動登録・変更・削除できる。買い物リストに現在表示されていない食材も価格変更できる。AIによる自動価格取得や外部サイトの巡回は行わない。
- 未購入・非除外の品目について税込購入予算の目安を計算する。個・袋などは購入単位ごとに切り上げ、g・mlは必要量に比例させる。価格未登録・単位不一致は未計算件数として明示し、合計は価格を計算できた品目のみの小計とする。購入済み・除外の品目は未購入予算から除く。
- 登録価格は買い物設定として端末に保存し、ドライブの設定バックアップ・自動同期に含める。買い物リストのスプレッドシート共有では価格表は送信しない。

## 家族共有

- 共有対象は「料理マスター」「買い物リスト」「献立」の3種類。Google Sheetsのファイルは種類ごとに独立して管理する。
- Google Drive上の共有ファイルを検索し、必要に応じて作成・権限付与・URLから接続を行う。共有する側と共有された側の接続状態を管理する。
- Google Drive APIの `drive.file` とSheets APIの権限を利用し、Googleアカウントの編集許可がある相手と共有する。
- 端末間の共有処理では更新の差分・操作履歴・状態の照合を扱う。実際の外部ファイル更新にはオンライン接続と有効な認証が必要。

## 設定・ドライブバックアップ

- 設定のカテゴリはカレンダー、献立、料理、買い物、データ・共有、AI、外観。7つの下部カテゴリボタンを共通バーに表示し、各タブと同じアイコンを利用する。
- 設定カテゴリの切り替え画面にはカテゴリ名だけの重複見出しを置かず、各設定セクションの見出しだけを表示する。セクション見出しの「？」から、そのセクション内の小項目に関する注意事項もまとめて確認できる。小項目には個別のヘルプボタンを設けない。実装詳細とデータ形式はREADMEに記載する。
- 設定のドライブバックアップは非公開のアプリ専用領域（`appDataFolder`）に保存する。対象には分類、カレンダー割当、アイコンプリセット、生成ルール、テーマ、下書き、料理マスターの手動情報、買い物設定などを含む。
- Googleカレンダーの取得済みイベント、端末の認証トークン、Googleカレンダー本体のデータは設定バックアップに含めない。
- 手動バックアップ・復元のほか、各端末で有効化する双方向の自動同期に対応。起動時・復帰時・変更後・表示中の間隔更新で照合する。最後に両者が一致した設定のスナップショットを端末に保持し、別々の項目や買い物・献立の独立した変更は3方向比較で統合する。同じ項目への相反する変更は上書きせず確認を求める。共通の履歴が残っていない古い競合は安全のため手動で解決する。同一競合の警告は定期的に繰り返さない。
- 設定ファイルの書き出し・読み込みも用意する。Googleカレンダーの履歴は含めない。
- 端末固有の表示や保存情報は `src/storage.js`、Driveの設定スナップショットは `src/drive-backup.js`、同期時の判断は `src/drive-sync.js` に分離している。

## UI・PWA

- レスポンシブレイアウトでスマホの操作を優先し、共通の固定ステータスバーに警告・エラー・認証状態を集約する。必要な詳細はダイアログで表示する。
- 献立・料理・買い物の上部操作行は揃える。カレンダー・料理・買い物・設定の下部操作行には共通の領域とボタン形状を用い、献立タブにも同じ高さの空の下部領域を確保する。下部領域に操作がない場合は空のままとし、画面の主要一覧だけを必要に応じてスクロールする。
- テーマは7色系統とそれぞれの明るめ／暗め、ライト・ダーク・OS追従に対応。アイコン色は画面テーマに連動する。
- Service Workerがアプリ内の静的資材をキャッシュする。初回オンライン接続が必要で、Google APIや認証処理をオフライン再生しない。
- オフライン時には端末に保存された下書きなどは扱えるが、実績をGoogleへ保存するには再接続が必要。イベント履歴は再読み込み後に再取得する。

## テストと検証範囲

- `npm test` はNodeのテストランナーを使い、データ変換、献立検証、同期・競合判断、画面出力、認証例外処理、各画面の回帰などをテストする。
- `npm run build` は公開用の `dist/` を生成。GitHub Actionsはテスト成功後にPagesへ公開し、バージョン付きリリースを生成する。
- 自動テスト内のGoogle API等はモックを使用するため、実アカウントでの認証・権限付与・実際のGoogle側の保存・iOS/Android実機挙動は別途検証が必要。
